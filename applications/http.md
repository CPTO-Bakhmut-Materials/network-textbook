# HTTP

## Коротка історія HTTP

У 1989 році Тім Бернерс-Лі (Tim Berners-Lee) працював у CERN (дослідницькій лабораторії у Швейцарії), і йому потрібно було обмінюватися інформацією між науковцями. Тоді вже існували протоколи на кшталт FTP для передавання файлів через Інтернет. Однак файл часто містить посилання на інші ресурси в Інтернеті. Його метою було створити протокол і формат файлів, що дозволяли б пов'язувати сторінки одна з одною й отримувати ці сторінки.

Оригінальна специфікація HTTP отримала номер версії HTTP/0.9 і вийшла в 1991 році. HTTP/1.0 стандартизували в 1996 році, а HTTP/1.1 — у 1997 році. Якщо не зазначено інше, у цьому розділі йдеться про HTTP/1.1, бо саме ця версія сьогодні використовується найчастіше. Існують і новіші версії (див. кінець цього розділу), але основи протоколу залишаються незмінними понад 20 років.


## Основи HTTP

HTTP працює поверх TCP. Двоє, хто хоче надсилати дані через HTTP, спершу встановлюють з'єднання TCP. Потім вони можуть використовувати його абстракцію потоку байтів, щоб надійно обмінюватися даними довільної довжини. Хостам, що працюють з HTTP, не треба перейматися тим, що пакети переупорядковуються, відкидаються тощо.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-13-http-bytestream.png">

HTTP — **клієнт-серверний** (client-server) протокол. Ми призначаємо одного учасника клієнтом (наприклад, вас, кінцевого користувача), а іншого — сервером (наприклад, Google, сайт банку тощо). Клієнт майже завжди працює з HTTP у веббраузері (наприклад, Firefox чи Chrome), хоча HTTP можна використовувати й інакше (наприклад, безпосередньо в терміналі).

Під час встановлення з'єднання HTTP сервер має слухати запити на з'єднання на загальновідомому сталому порту з номером 80. (HTTPS, новіша захищена версія, використовує порт 443.) Клієнт може обрати будь-який випадковий ефемерний номер порту, щоб розпочати з'єднання, і сервер може надсилати відповіді на цей номер порту.

HTTP — протокол **«запит–відповідь»** (request-response). На кожен запит, який надсилає клієнт, сервер надсилає рівно одну відповідну відповідь.


## Запити HTTP

Повідомлення запиту HTTP форматується як зрозумілий людині звичайний текст, тобто ви можете вводити сирі запити HTTP у терміналі. Запит містить три частини: метод, URL, версію, а також необов'язковий вміст.

Повідомлення закінчується символом нового рядка (технічно це CRLF; пошукайте, якщо цікаво), що можна уявляти як натискання користувачем клавіші Enter після введення запиту HTTP у терміналі.

Номер версії вказує, яку версію HTTP ви використовуєте, наприклад HTTP/0.9, HTTP/1.0, HTTP/1.1 тощо.

Запитаний URL ідентифікує ресурс на сервері. URL можна уявляти як шлях до файлу, який ви намагаєтеся отримати з віддаленого сервера. Наприклад, в URL http://cs168.io/assets/lectures/lecture1.pdf ми намагаємося отримати файл у теці assets/lectures з назвою lecture1.pdf на віддаленому сервері cs168.io. (Сервери не зобов'язані працювати саме так, але така інтуїція корисна.)

Метод визначає, яку дію хоче виконати користувач. Спочатку HTTP мав лише один метод, GET, що дає клієнтові змогу отримати з сервера конкретну сторінку (вказану URL).

Пізніше HTTP розширили іншими методами. Зокрема, додали метод POST, що дає клієнтові змогу також передавати інформацію серверу. Наприклад, якщо користувач заповнює форму й натискає «Надіслати», ці дані надсилаються серверу в запиті POST.

Існують і менш уживані методи. HEAD отримує заголовки (метадані) відповіді, але не власне вміст відповіді. Інші методи, як-от PUT, CONNECT, DELETE, OPTIONS, PATCH і TRACE, перетворюють HTTP на протокол, що дає користувачеві змогу взаємодіяти з вмістом на сервері. Тепер користувач може змінювати вміст, на відміну від початкового дизайну, де користувач міг лише отримувати вміст. Ці додаткові методи роблять HTTP дуже гнучким для найрізноманітніших застосунків.

Зауважте, що з іншими методами, як-от POST, ми однаково маємо вказати URL, щоб позначити, як інтерпретувати дані, які ми надсилаємо. На сайті банку надсилання імені на URL /send-money, імовірно, зробить щось інше, ніж надсилання того самого імені на URL /request-money.

Для запитів GET вміст запиту зазвичай порожній, бо ми просимо сторінку в сервера й не надсилаємо жодної власної інформації. Натомість для запиту POST вміст запиту містить дані, які ми хочемо надіслати серверу.


## Відповіді HTTP

Кожному запиту HTTP відповідає одна відповідь HTTP. Відповідь теж є зрозумілим людині звичайним текстом, тобто ви можете читати сирі відповіді HTTP в терміналі. Відповідь містить чотири частини: версію, код стану, необов'язкове повідомлення і вміст.

Як і раніше, версія вказує версію HTTP, що використовується.

У вміст сервер поміщає, наприклад, сторінку, яку користувач запитав у запиті GET.

Код стану (status code) — число, що дає серверу змогу вказати результат запиту клієнта. Кожен код стану має відповідне зрозуміле людині повідомлення.

Коди стану поділяються на різні категорії за числовими значеннями:

100 = Інформаційні відповіді.

200 = Успішні відповіді. 200 OK вказує на успішний запит, де визначення успіху залежить від методу запиту та застосунку, що використовує HTTP (пам'ятайте, коди стану є в кожній відповіді, незалежно від методу запиту — GET/POST тощо). 201 Created вказує, що запит успішний і було створено певний новий ресурс. Зазвичай це трапляється в запитах POST чи PUT.

300 = Повідомлення про перенаправлення. Вони дають серверу змогу повідомити клієнтові, що той має шукати ресурс (вказаний URL) деінде. Два поширені — 301 Moved Permanently і 302 Found (дивна назва для «тимчасово переміщено»). Іноді сам код стану не дає достатньо контексту (як видно з цих перенаправлень). Тому відповідь також міститиме додаткову інформацію про те, куди переміщено ресурс (наприклад, інший URL).

Використання конкретніших кодів стану дає клієнтові змогу визначати свою подальшу поведінку на основі коду. Наприклад, 301 Moved Permanently каже клієнтові припинити шукати в початковому місці, а 302 Found (тимчасово переміщено) може підказати клієнтові повернутися й перевірити знову пізніше.

400 = Помилка, спричинена діями клієнта. 401 Unauthorized каже, що клієнтові не дозволено доступ до цього вмісту, але якщо він підтвердить свою особу (наприклад, увійде в систему), то, можливо, зможе отримати доступ. 403 Forbidden каже, що клієнт автентифікований і сервер знає його особу, але йому однаково не дозволено доступ до вмісту.

Знову ж таки, використання конкретніших кодів дає клієнтові змогу визначати подальшу поведінку. 401 Unauthorized може змусити браузер клієнта показати вікно входу, а 403 Forbidden — показати повідомлення про помилку (бо користувач уже ввійшов).

500 = Помилка, спричинена діями сервера. Поширені 500 Internal Server Error і 503 Service Unavailable. Клієнт мало що може вдіяти з цими помилками, хіба що спробувати знову пізніше.

Деякі коди помилок, як-от 404 (File Not Found) і 503 (Service Unavailable), дуже впізнавані.

Іноді те, який код стану доречно використати, може бути неоднозначним. Наприклад, якби ми надіслали Google запит HTTP версії 0.9, доречним міг би бути 505 (HTTP Version Not Supported). Натомість Google відповідає 400 (Bad Request). Зазвичай мета — надати помилку з правильної категорії (наприклад, 400 і 500 вказують на помилки), що спричинить правильну поведінку клієнта.


## Заголовки HTTP

Якщо клієнт має додаткову інформацію, яку хоче надіслати серверу, він може включити додаткові метадані, які називаються **заголовками** (headers). У HTTP/1.1 жоден заголовок не обов'язковий, тож цілком допустимо не включати жодного (хоча сервер/клієнт може очікувати заголовок і видати помилку).

Наприклад, заголовок Location можна використовувати у відповідях HTTP 300, щоб вказати, куди переміщено ресурс.

Іноді інформація в заголовку необов'язкова. Наприклад, заголовок User-Agent у запиті дає клієнтові змогу повідомити серверу про браузер чи програму клієнта (наприклад, Firefox чи Chrome). Це може дозволити обробляти запит по-різному залежно від поля заголовка (наприклад, чи користувач у Chrome, чи в терміналі).

Іншим разом інформація в заголовку критичніша. Наприклад, Content-Type повідомляє, чи є корисне навантаження HTML-сторінкою, зображенням, відео тощо. Це підказує браузеру, як відображати відповідь HTTP. Якщо сервер розміщує кілька вебсайтів, у запитах можна використовувати заголовок Host, щоб вказати, який вебсайт запитується.

Деякі заголовки стосуються запитів. Вони дають клієнтові змогу передавати інформацію серверу. Наприклад, заголовок Accept дає клієнтові змогу повідомити серверу, який тип вмісту клієнт очікує (наприклад, HTML для зрозумілих людині сторінок, JSON для машинно розбірних даних). Заголовок User-Agent вказує тип клієнта, що використовується, а заголовок Host — конкретний хост, до якого звертаються (на випадок, якщо сервер розміщує кілька вебсайтів). Заголовок Referer вказує, як клієнт зробив запит (наприклад, чи натиснув він посилання з Facebook, щоб зробити цей запит).

Інші заголовки стосуються відповідей. Пам'ятайте, заголовки — це метадані про вміст, а не сам вміст. Наприклад, Content-Encoding повідомляє, як слід інтерпретувати біти відповіді (наприклад, Unicode/ASCII для зрозумілого людині тексту чи gzip для стисненого файлу). Заголовок Date повідомляє, коли сервер згенерував відповідь.

Деякі заголовки є заголовками представлення (representation headers), які використовуються і в запитах, і у відповідях, щоб описати, як представлено вміст. Наприклад, заголовок Content-Type вказує тип документа (наприклад, текст, зображення) і може бути в запитах POST чи у відповідях GET. Заголовки представлення дають змогу переносити через HTTP різні типи вмісту, що дозволяє узагальнити протокол і зробити його придатним для найрізноманітніших застосунків.


## Приклади HTTP

У терміналі можна ввести `telnet google.com 80`, щоб під'єднатися до порту 80 (HTTP) на сервері Google. Потім термінал дасть змогу ввести сирий запит HTTP із заголовками, наприклад:

`GET / HTTP/1.1`

`User-Agent: robjs`

Це запит GET кореневої сторінки на сервері за протоколом HTTP версії 1.1. Заголовок User-Agent вказує тип клієнта, який ми використовуємо.

Так само відповідь теж зрозуміла людині.

`HTTP/1.1 200 OK`

`Date: Sat, 16 Mar 2024 18:33:08 GMT`

`Content-Type: text/html; charset=ISO-8859-1`

`<!doctype html><html lang="en"><head><meta content="Search the world's information, including webpages, images, videos and more. Google has many special features to help you find exactly what you're looking for." name="description">...`

`HTTP/1.1 200 OK` повідомляє нам версію та код стану (200) з відповідним повідомленням (OK). Додано два заголовки: дату відповіді й тип вмісту. Потім вміст містить сирий HTML вебсторінки. Якби ми відкрили цей HTML у веббраузері, він виглядав би як справжня вебсторінка.

<img width="800px" src="{{ site.baseurl }}/assets/applications/4-14-httpexample1.png">

<img width="800px" src="{{ site.baseurl }}/assets/applications/4-15-httpexample2.png">

Ось кілька інших прикладів. Зверніть увагу, що розділ вмісту порожній у запиті GET, але містить дані в запитах POST і PUT. І навпаки, відповіді на POST і PUT не мають вмісту, а відповідь на GET має.

Код стану й заголовок повідомляють корисні метадані про запит. Наприклад, стан 201 Created повідомляє, що надісланий нами файл успішно збережено на сервері. Заголовок повідомляє, де на сервері збережено файл (і ми можемо використати це розташування, щоб отримати файл пізніше).


## Прискорення HTTP за допомогою конвеєризації

Завантаження однієї сторінки у веббраузері може потребувати кількох запитів HTTP. Коли ви запитуєте відео на YouTube, ваш браузер має зробити окремі запити для самого відео, HTML з іншим текстом на вебсторінці (наприклад, назвою відео, коментарями), мініатюр пов'язаних відео тощо. Багато з цих запитів, імовірно, ідуть до того самого сервера (у цьому випадку — сервера YouTube).

Пригадайте, що HTTP працює поверх TCP. У наївному випадку кожен окремий запит потребував би встановлення нового з'єднання TCP із тристороннім рукостисканням. Після запиту ми закриваємо з'єднання, а потім одразу знову виконуємо рукостискання для наступного запиту.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-16-no-pipeline.png">

HTTP 1.1 оптимізував це, дозволивши конвеєризувати (pipeline) кілька запитів і відповідей HTTP в тому самому з'єднанні. Тепер нам більше не потрібне окреме з'єднання TCP (з окремим рукостисканням) для кожного запиту.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-17-pipeline.png">

Один недолік цієї оптимізації полягає в тому, що сервер тепер має тримати більше одночасно відкритих з'єднань. Серверу потрібен певний спосіб закривати з'єднання за тайм-аутом. Якщо сервер перевантажений відкритими з'єднаннями, клієнт може отримати помилку на кшталт 503 Service Unavailable. Зловмисники можуть використати це в атаці типу «відмова в обслуговуванні».


## Прискорення HTTP за допомогою кешування: типи

Ще одна стратегія прискорення HTTP — кешування відповідей, щоб не робити повторних запитів тих самих даних.

Якщо ми не кешуємо, кожен запит має дістатися сервера.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-18-nocache.png">

Є три типи кешів HTTP:

**Приватні кеші** (private caches) пов'язані з конкретним кінцевим клієнтом, що під'єднується до сервера (наприклад, кеш у вашому власному браузері). Тепер, якщо той самий користувач запитує той самий ресурс удруге, він може отримати ресурс зі свого локального кешу. Однак приватні кеші не діляться між користувачами.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-19-privatecache.png">

**Проксі-кеші** (proxy caches) розташовані в мережі (не на кінцевому хості), і їх контролює оператор мережі, а не постачальник застосунку. Ці кеші можуть спільно використовувати багато користувачів, тож користувач, що запитує ресурс уперше, може отримати дані з проксі-кешу, а не з вихідного сервера (origin server).

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-20-proxycache.png">

Одна проблема проксі-кешів полягає в тому, що клієнтів треба якось перенаправляти до проксі-кешу. Проксі-кеш обслуговує не застосунок, тож вихідний сервер не обов'язково знає про проксі-кеш. Оператору мережі потрібен певний спосіб контролювати кінцевого клієнта, щоб повідомити його про проксі-кеш.

Один поширений підхід — неправдиві відповіді DNS, що можливо, якщо оператор мережі контролює і проксі-кеш, і рекурсивний резолвер. Коли клієнт робить запит до вихідного сервера, він має знайти IP-адресу вихідного сервера. Рекурсивний резолвер може збрехати й сказати: «IP-адреса вихідного сервера — 1.2.3.4 (IP-адреса проксі-кешу)». Тепер запити до вихідного сервера йдуть натомість до проксі-кешу, який може обслуговувати кешовані відповіді. Або, якщо запитаного ресурсу немає в проксі-кеші, проксі-кеш може зробити запит до вихідного сервера, а потім кеш може віддати результат користувачеві.

Ще одна проблема проксі-кешів полягає в тому, що застосунок не керує проксі-кешем. Вихідний сервер має довіряти тому, що проксі-кеш робить усе правильно (наприклад, дотримується термінів дії кешу, видає правильні дані).

**Керовані кеші** (managed caches) розташовані в мережі, і їх контролює постачальник застосунку. Зауважте, що сервери керованого кешу розгортаються окремо і не є початковим сервером, що згенерував вміст. Оскільки ці кеші контролює постачальник застосунку, це дає застосунку більше контролю.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-21-managedcache.png">

Оскільки застосунки контролюють і вихідний сервер, і кеш, вони можуть самі перенаправляти користувачів до кешів. Наприклад, якщо ви запитуєте сторінку відео YouTube з вихідного сервера, відповідь може містити HTML (назву відео, коментарі). Потім HTML може містити посилання, що конкретно вказують отримувати відео й зображення з проксі-кешів (наприклад, завантажувати зі static.youtube.com замість www.youtube.com).

## Прискорення HTTP за допомогою кешування: переваги й недоліки

Кешування корисне для всіх. Клієнт швидше завантажує сторінки, бо може уникати повторних запитів і користуватися розташованими поруч проксі. Провайдери виграють, бо мережею надсилається менше запитів/відповідей HTTP, тож вони можуть будувати меншу пропускну здатність. Сервери виграють, бо користувачі роблять менше запитів, і серверам не треба обробляти стільки запитів.

Клієнтам, провайдерам і серверам усім важливо забезпечити клієнтові добру продуктивність. Клієнт хоче дивитися відео у високій якості, а провайдери й застосунки отримають більше клієнтів, забезпечуючи добру продуктивність. Кешування допомагає всім цього досягти, бо запит клієнта може ефективніше обслуговуватися з ближчого кешу (локального чи в мережі) з меншою латентністю. Крім того, пригадайте, що пропускна спроможність TCP і RTT обернено пропорційні, тож коротший RTT до ближчого сервера означає вищу пропускну спроможність. Це особливо корисно для великого вмісту, як-от відео.

Міркуючи про кешування, треба враховувати, чи змінюватиметься вміст у майбутніх запитах. Деякі ресурси HTTP статичні. Якщо ви запитуєте логотип Google, він залишається тим самим у кількох запитах.

Інші ресурси HTTP динамічні. Якщо ви робите пошуковий запит Google, відповідь може змінюватися залежно від того, хто й коли питає. Сервер має динамічно генерувати іншу відповідь для кожного запиту.

Деякі ресурси статичні, і їх можна кешувати й обслуговувати з проксі-кешів чи керованих кешів, тоді як інші ресурси мають генеруватися динамічно. Наприклад, якщо ви робите пошук Google, HTML-відповідь, найімовірніше, має динамічно генерувати вихідний сервер. Однак HTML може містити посилання для отримання логотипа Google — статичного ресурсу — з одного із серверів керованого кешу.

Зручно, що більші ресурси, як-от зображення й відео, статичні, і їх можна агресивно кешувати. Динамічний вміст, як-от персоналізовані HTML-сторінки, як правило, менший. Клієнти можуть запитувати динамічний вміст у вихідного сервера (далеко), а для всього статичного вмісту використовувати кеші й проксі (ближче).


## Прискорення HTTP за допомогою кешування: реалізація

Щоб реалізувати кешування, нам знадобиться використовувати заголовки для перенесення певних метаданих про кешування (наприклад, як довго кешувати дані). Це ще один приклад того, як заголовки забезпечують розширюваність початкового протоколу (який не підтримував кешування).

Початкова застаріла функціональність кешування в HTTP/1.0 використовувала заголовок Expires, який просто вказував, як довго дані можна кешувати. У HTTP/1.1 запровадили складніший заголовок Cache-Control. Для сумісності деякі вебсервери повертають дані з обома заголовками. Клієнти HTTP/1.0 не розумітимуть новішого заголовка Cache-Control і ігноруватимуть його. Клієнти HTTP/1.1 надаватимуть перевагу новішому заголовку Cache-Control над старішим Expires.

Заголовок Cache-Control вказує, які типи кешів можуть кешувати дані і як довго. Наприклад, якщо ресурс динамічний і змінюється для кожного користувача, але для конкретного користувача залишається незмінним у часі, сервер може відповісти: Cache-Control: private, max-age:86400. Це означає, що цей вміст слід зберігати лише в локальному кеші користувача (а не в спільних проксі-кешах чи керованих кешах), і зберігати його можна один день (86400 секунд).

Деякі дані не можна кешувати (наприклад, динамічний вміст, що часто змінюється). У такому разі сервер може встановити Cache-Control: no-store, щоб вказати, що клієнт і проксі не можуть кешувати вміст.

Заголовок Cache-Control необов'язковий, тож немає гарантії, що клієнт прочитає заголовок чи дотримуватиметься його. Цей заголовок можна уявляти як прохання сервера щось закешувати. Це особливо стосується проксі-кешів, які обслуговує не постачальник застосунку. Натомість приватний кеш обслуговує клієнт (тобто його браузер), і порушення правил впливає лише на самого клієнта. Керований кеш обслуговує той самий постачальник застосунку, тож він може забезпечити, щоб керовані кеші дотримувалися правил вихідного сервера.

Цей заголовок можна використовувати й для складніших політик. Наприклад, сервер може сказати: ви можете кешувати ці дані, але перш ніж використовувати кешовані дані, будь ласка, зробіть запит HTTP HEAD, щоб повторно запитати заголовок і повторно перевірити дані. Якщо заголовок вказує, що дані змінилися, анулюйте кеш.


## Мережі доставки вмісту (CDN)

Раніше ми бачили, що керовані кеші — добра стратегія кешування й покращення продуктивності для користувачів. На відміну від приватних кешів, вони спільні для користувачів (наприклад, користувача, що запитує щось уперше, може обслужити кеш). Крім того, на відміну від проксі-кешів, їх контролює постачальник застосунку, що дає застосунку більше контролю. Застосунок може гарантувати, що кеші дотримуються правил, встановлених вихідним сервером, а вихідний сервер може контролювати, до яких кешів перенаправляється користувач.

Розгортання керованих кешів по всій мережі приводить нас до ідеї **мереж доставки вмісту** (content delivery networks, CDN) — наборів серверів у мережі, що обслуговують вміст (наприклад, ресурси HTTP).

Для доброї продуктивності ми намагаємося розміщувати CDN близько до кінцевих користувачів. Тут «близько» означає географічно близько, але також близько з погляду мережі (менше переходів).

CDN дають нам усі переваги кешування. Користувачі отримують продуктивнішу доставку вмісту, бо сервери ближче. Ми можемо зменшити потрібну пропускну здатність і інфраструктуру мережі, бо користувачі надсилають більшість запитів до розташованих поруч серверів, а не до одного вихідного сервера (можливо, далекого).

CDN дають постачальникам змогу легше масштабувати свою серверну інфраструктуру. З одним вихідним сервером нам довелося б масштабувати цей сервер, роблячи його неймовірно потужним і даючи йому неймовірно високу пропускну здатність. Натомість із CDN ми можемо масштабуватися, просто додаючи більше невеликих серверів по всьому Інтернету.

CDN також забезпечують постачальникам кращу надлишковість. Якщо один вихідний сервер виходить з ладу, сервіс може стати недоступним. Натомість із CDN, якщо один сервер виходить з ладу, користувачів однаково можна перенаправити до інших серверів.


## Розгортання CDN

Пригадайте нашу модель Інтернету: запит клієнта пересилається через маршрутизатори глобальної мережі (WAN), що належать провайдерові, доки не дійде до точки пірингу. Потім запит іде до точки пірингу в мережі постачальника застосунку. Запит проходить мережами WAN застосунку, доки не дійде до мережі дата-центру, де розташований вихідний сервер.

Якщо ми не розгортаємо жодної CDN, кожен запит має дістатися вихідного сервера. Це дає максимальну латентність (порівняно з подальшими варіантами з CDN), що призводить до найнижчої продуктивності. Крім того, це вимагає проходження найбільшої пропускної здатності, тобто нам доводиться будувати більше пропускної здатності. Нарешті, це вимагає, щоб вихідний сервер масштабувався для обробки кожного запиту.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-21-cdn1.png">

Кращим варіантом було б розгорнути певні сервери CDN на краю мережі постачальника застосунку. Наприклад, якщо мережа Google має піринг із мережами провайдерів у Нью-Йорку, ми могли б розмістити там певні CDN.

Тепер обсяг трафіку, що передається мережею постачальника застосунку, набагато менший. Вихідний сервер надсилає відео до CDN один раз, і CDN може віддавати це відео багатьом користувачам. Мережі застосунку більше не треба масштабувати свою мережу WAN.

Крім того, як ми бачили раніше, тепер ми можемо масштабуватися, додаючи більше CDN, а не модернізуючи один вихідний сервер. У нас також більше надлишковості.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-22-cdn2.png">

Можна зробити ще краще й просунути кешування глибше в мережу. Тепер застосунок розгортає сервери всередині мережі провайдера.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-23-cdn3.png">

Чому провайдер погодився б дозволити застосунку розгорнути CDN у своїй мережі? Виявляється, це взаємовигідно для всіх. Клієнти провайдера отримають кращу продуктивність, бо зможуть користуватися цією новою ближчою CDN. Крім того, інтенсивний трафік між користувачами й CDN тепер повністю залишається в межах мережі провайдера. Це означає, що провайдерові потрібна менша пропускна здатність у піринговому з'єднанні між провайдером і застосунком (бо вміст передається цим піринговим з'єднанням лише один раз).

На практиці провайдер і CDN часто співпрацюють у розгортанні серверів. Наприклад, застосунок надає сервери безкоштовно, а провайдер безкоштовно під'єднує сервер до мережі. У деяких випадках провайдерові й CDN треба домовлятися про певну оплату (від CDN провайдерові чи від провайдера CDN) залежно від того, де в мережі розгорнуто сервер, і від вартості сервера та під'єднання. Утім, обидві сторони зацікавлені в розгортанні цих серверів.

Можна спробувати піти ще далі, але зрештою ми стикаємося з компромісами між витратами й вигодою. У найекстремальнішому випадку ми могли б розгорнути CDN у кожному домі, але витрати, найімовірніше, переважать вигоду. Зокрема, CDN працюють найкраще, коли ними користуються кілька користувачів. Сукупний кеш більший, а одне розгортання може охопити багатьох користувачів.

<img width="900px" src="{{ site.baseurl }}/assets/applications/4-24-cdn4.png">

Загальніше, є компроміс між вартістю додавання нових CDN і грошима, які ви заощаджуєте, будуючи меншу пропускну здатність. На практиці CDN таки існують у мережах провайдерів, бо їх однаково вигідно там встановлювати.

Звіт Sandvine (компанії, що займається інспекцією пакетів) за 2023 рік показав, що 15% усього інтернет-трафіку припадає на Netflix, 11,4% — на YouTube, а 4,5% — на Disney+. Якщо провайдер встановить у своїй мережі сервери лише для цих трьох застосунків, він потенційно може будувати на 25% менше пропускної здатності мережі.

Великі постачальники застосунків, як-от Google, Netflix, Amazon і Facebook, розгортають CDN і у власних мережах, і в мережах провайдерів.

Якщо ви постачальник застосунку, ви можете не бути технологічним гігантом на кшталт Google чи Amazon, але однаково хочете, щоб ваш вміст обслуговувався через CDN для доброї продуктивності. Такі менші застосунки, найімовірніше, не можуть дозволити собі встановлювати власні CDN. Однак компанії на кшталт Cloudflare, Akamai та Edgio розгорнули CDN, і ви можете заплатити цим компаніям, щоб вони розмістили ваш вміст у своїй наявній CDN. Ці постачальники CDN також розгортають інфраструктуру і у власних мережах, і в мережах провайдерів.

CDN можуть використовувати й провайдери, бо провайдери самі можуть мати застосунки, що обслуговують вміст. Коли ви платите за інтернет-послуги, провайдер може також пропонувати телевізійні послуги (пряме ТБ чи відео на замовлення). Такі провайдери встановлюють власні CDN, щоб ефективно доставляти вам цей телевізійний вміст.

По суті, сервери в CDN такі самі, як будь-які інші сервери в Інтернеті, що надають вміст, хоча вони часто дуже оптимізовані для зберігання й доставки великих обсягів вмісту. Деякі сервери можуть краще зберігати й обслуговувати великі обсяги вмісту, а інші — краще швидко обслуговувати менші фрагменти вмісту великій кількості клієнтів.


## Спрямування клієнтів до кешів

У CDN багато різних серверів по всьому Інтернету надають той самий вміст. Як клієнт дізнається, до якого сервера звертатися?

Деякі прийоми з DNS можна застосувати й до CDN. Можна використати anycast, коли кілька серверів оголошують той самий IP-префікс. Це дає алгоритму маршрутизації змогу знайти найкращий шлях до будь-якого з серверів.

<img width="800px" src="{{ site.baseurl }}/assets/applications/4-25-anycast1.png">

Одна проблема anycast пов'язана з довготривалими з'єднаннями. Припустімо, клієнт має поточне з'єднання TCP з одним із серверів. Під час з'єднання якийсь проміжний канал у мережі відмовляє. Оскільки всі сервери мають ту саму IP-адресу, з погляду проміжного маршрутизатора пересилання до будь-якого з серверів коректне. Тепер проміжний маршрутизатор може почати пересилати пакети іншому серверу (з тією самою IP-адресою). Однак з'єднання TCP було з початковим сервером, і цей новий сервер ніяк не може продовжити початкове з'єднання.

Зауважте, що ця проблема не стосувалася використання anycast у DNS, бо з'єднання DNS дуже короткі (зазвичай лише один пакет UDP).

<img width="800px" src="{{ site.baseurl }}/assets/applications/4-26-anycast2.png">

Для балансування навантаження можна також використати DNS. На відміну від anycast, сервери тепер мають різні IP-адреси, хоча всі однаково мають той самий домен. Коли клієнт запитує відображення «домен–IP», сервер імен DNS може надати іншу IP-адресу залежно від розташування клієнта.

Цей підхід на основі DNS не має проблеми anycast із довготривалими з'єднаннями, бо сервери тепер мають різні адреси. Маршрутизатор не почне раптом пересилати пакети іншому серверу.

Одна проблема підходу на основі DNS — брак деталізації. Як екстремальний приклад, припустімо, що всі в мережі провайдера Comcast використовують той самий рекурсивний резолвер. Це означає, що всі надсилають свої DNS-запити резолверу, який потім надсилає запит серверу імен застосунку. Сервер імен застосунку бачить лише, що DNS-запит надійшов від Comcast, і мусить повернути Comcast одну IP-адресу. Тепер кожен користувач у мережі Comcast використовує той самий сервер, навіть якщо користувачі розкидані по всьому світу.

Надійніший за anycast чи DNS підхід — відображення на рівні застосунку. Коли вихідний сервер отримує запит HTTP, посилання у відповіді можуть вказувати на різні сервери (наприклад, static1.google.com чи static2.google.com — два сервери в різних місцях) залежно від того, звідки надійшов запит. Або вихідний сервер може відповісти кодом стану HTTP рівня 300, щоб перенаправити користувача до відповідного сервера.

Цей підхід на рівні застосунку не має проблеми деталізації DNS, бо застосунок бачить адресу клієнта в запиті HTTP. Він також не має проблеми anycast, бо різні сервери можуть мати різні IP-адреси.

Однак, як і в балансуванні навантаження через DNS, застосунку однаково потрібен певний спосіб вгадати найближчий до клієнта сервер (де «близько» може бути географічно або на основі топології мережі).

Одна перевага відображення на рівні застосунку — додаткова деталізація залежно від вмісту. Наприклад, популярні відео можна розгорнути на багатьох серверах, даючи кожному клієнтові змогу отримувати відео з розташованого поруч сервера. Натомість непопулярні відео, до яких звертаються рідко, можна розгорнути на меншій кількості серверів, і користувачам доведеться йти по вміст далі.


## Новіші версії HTTP

Зі зростанням Інтернету HTTP почали використовувати дедалі більше застосунків, бо це дуже універсальний протокол.

Згодом безпека HTTP ставала дедалі більшою проблемою. Сервер банку, що працює з HTTP, найімовірніше, не хоче, щоб інформація надсилалася мережею зрозумілим людині звичайним текстом, де її можуть прочитати проміжні маршрутизатори чи зловмисники.

HTTPS — розширення HTTP, що додає безпеку. Протокол під назвою TLS (Transport Layer Security, безпека транспортного рівня) побудовано поверх TCP: користувачі обмінюються секретними ключами й шифрують повідомлення, перш ніж надсилати їх потоком байтів. HTTPS має той самий фундаментальний протокол, але тепер працює поверх TLS (який сам працює поверх TCP), а не безпосередньо поверх сирого незахищеного TCP. Останніми роками вебсайти активно спонукають переходити на HTTPS, і станом на 2024 рік понад 85% вебсайтів за замовчуванням використовують HTTPS.

HTTP/2.0 запровадили в 2015 році, і це була перша суттєва редакція протоколу з 1997 року. Головною метою редакції було покращити продуктивність, зменшивши латентність і прискоривши завантаження сторінок.

HTTP/2.0 запровадив проштовхування з боку сервера (server-side pushing), коли сервер може надіслати відповідь, навіть якщо клієнт не робив запиту. Це дає серверу змогу передбачати й завчасно надавати те, що може знадобитися користувачеві, не чекаючи, поки користувач зробить запит. Наприклад, якщо ми робимо пошук Google, повертається HTML результатів. Потім браузер користувача розбирає HTML, з'ясовує, що йому потрібен логотип Google, і робить ще один запит HTTP. З HTTP/2.0 сервер може завчасно надати користувачеві логотип Google, не чекаючи запиту.

HTTP/2.0 мав і інші покращення продуктивності. Заголовки можна стискати, щоб заощадити місце. Запитам і відповідям можна встановлювати пріоритети, щоб високопріоритетний вміст (наприклад, текст результатів пошуку) доставлявся раніше за низькопріоритетний (наприклад, логотип Google). Одночасні запити можна ефективніше мультиплексувати. Якщо перший запит має відповідь на 4 ГБ, а другий — на 1 КБ, наївна реалізація може змусити другу відповідь застрягнути в очікуванні завершення першої. HTTP/2.0 дає змогу розумніше керувати цими відповідями.

HTTP/2.0 широко прийнятий і клієнтами (наприклад, сучасними браузерами), і серверами (наприклад, CDN).

HTTP/3.0 запровадили в 2022 році (незабаром після HTTP/2.0, порівняно з проміжком між 1.1 і 2.0). Семантика така сама, як у HTTP/2.0, але він замінює базовий протокол транспортного рівня. Замість працювати поверх потоку байтів TCP, HTTP/3.0 працює поверх нового транспортного протоколу під назвою QUIC, спеціально створеного для доброї роботи з HTTP/3.0. QUIC = Quick UDP Connections; його спроєктували в Google і стандартизували в IETF.

HTTP/3.0 — приклад того, як ми навмисно відмовляємося від однієї з ключових мережевих парадигм (розбиття на рівні) заради кращої ефективності. Даючи проєктувальникам свободу налаштовувати під себе і протокол транспортного рівня (QUIC), і протокол прикладного рівня (HTTP/3.0), ми можемо спроєктувати обидва протоколи так, щоб вони добре працювали разом.
